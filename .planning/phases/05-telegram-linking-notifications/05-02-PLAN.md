<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Internal app event → sender function | Caller can provide malformed template/event input |
| Scheduled secret caller → internal reminder functions | Secret-protected system caller triggers bulk sends |
| Edge Functions → Telegram HTTP API | Third-party API responses are untrusted and may fail |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-08 | S | recipient targeting | mitigate | Resolve recipients from `telegram_accounts` + `notification_preferences`, never from caller-supplied chat IDs. |
| T-05-09 | T | template/event payloads | mitigate | Whitelist template codes and SQL-derived payload shapes before rendering or dispatch. |
| T-05-10 | R | delivery accountability | mitigate | Persist one `notification_deliveries` row per attempt with status, error, and Telegram message id metadata. |
| T-05-11 | I | proof/privacy leakage | mitigate | Exclude proof files/URLs from all Telegram payload builders and keep web app as the only detailed record surface. |
| T-05-12 | D | retry storms / job duplication | mitigate | Do not retry failed sends in v1 and enforce monthly reminder dedupe in SQL. |
| T-05-13 | E | internal job abuse | mitigate | Require `APP_INTERNAL_CRON_SECRET` for scheduled endpoints and keep them JWT-protected otherwise. |
| T-05-14 | D | upstream workflow blocking | mitigate | Catch and log delivery failure without rolling back payment verification or announcement publish. |
</threat_model>
