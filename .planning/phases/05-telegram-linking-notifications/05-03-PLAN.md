<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram sender → webhook command handler | Untrusted command text and sender metadata enter privileged read paths |
| Resident settings UI → link issuer | Resident-triggered linking actions cross into Edge Function issuance |
| Admin browser → template/delivery admin UI | Privileged template edits and delivery views rely on RLS + audit enforcement |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-15 | S | webhook command identity | mitigate | Resolve sender from linked `telegram_user_id` and reject unknown/unlinked accounts with the D-10 message. |
| T-05-16 | I | resident command replies | mitigate | Query billing/payment data strictly through the linked profile's kavling scope and never expose proof URLs/files. |
| T-05-17 | T | unlink / relink flows | mitigate | Require explicit text confirmation for `/unlink` and keep relink issuance inside authenticated settings UI only. |
| T-05-18 | E | admin summary command | mitigate | Require linked admin-like role before serving `/admin` snapshot output. |
| T-05-19 | R | template mutations | mitigate | Log template create/update/reset actions via `writeAuditLog` with before/after data. |
| T-05-20 | I | admin delivery visibility | mitigate | Keep `/admin/telegram` under admin/super_admin navigation and rely on existing RLS for delivery/template data. |
</threat_model>
