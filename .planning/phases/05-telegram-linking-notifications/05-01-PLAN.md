<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Resident browser → `link-telegram-account` | Authenticated resident requests a privileged link token |
| Telegram webhook → `telegram-bot-webhook` | Untrusted external payload enters the public consume path |
| Edge Functions → Postgres | Service-role code can mutate sensitive linkage tables |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01 | S | link token issuance | mitigate | Store SHA-256 hash only, never plain tokens, and issue deep links from authenticated resident context only. |
| T-05-02 | T | token consume contract | mitigate | Bind consume path to token-owned `profile_id`; reject any caller-controlled profile override. |
| T-05-03 | R | link event trail | mitigate | Persist issue/consume timestamps and document audit-visible linkage state transitions. |
| T-05-04 | I | token replay/leakage | mitigate | Enforce 15-minute expiry, invalidate prior unused tokens for same profile, and set `consumed_at` on first success only. |
| T-05-05 | D | webhook abuse | mitigate | Reject missing/wrong secret token before parsing body and keep response body generic on invalid links. |
| T-05-06 | E | public webhook exposure | mitigate | Scope `verify_jwt = false` only to `telegram-bot-webhook`; keep all other Telegram functions authenticated or secret-gated. |
| T-05-07 | T | cross-account link conflict | mitigate | Surface `telegram_user_id` uniqueness conflict as the D-18 message and do not overwrite another profile's account. |
</threat_model>
