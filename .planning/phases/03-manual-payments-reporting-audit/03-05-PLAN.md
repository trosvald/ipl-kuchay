<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| resident invoice-detail UI → payment/receipt queries | Resident-facing history must show only their own invoice/payment/receipt rows. |
| admin reports UI → report-output generation/download actions | Finance operators trigger privileged artifact generation and access from client-side controls. |
| generated output history → reconciliation messaging | Stale or failed output loads can mislead operators if the UI hides divergence. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-18 | I | `ResidentReceiptHistory` download actions | mitigate | Use signed-URL calls only after RLS-filtered receipt-history queries; never render raw `file_path` or public URLs. |
| T-03-19 | T | `ReportsPage` receipt-candidate generation actions | mitigate | Generate one receipt per invoice/payment candidate and refresh output history immediately so operators see exact artifact truth, not stale optimistic state. |
| T-03-20 | R | report freshness and reconciliation messaging | mitigate | Show `Terakhir diperbarui`, manual refresh, and inline warning/retry UI whenever artifact generation or reload diverges per D-12/D-13. |
| T-03-21 | D | resident/admin history screens | accept | Additional queries are invoice/period scoped and neighborhood-scale; bounded lists keep load cost low. |
| T-03-22 | E | resident invoice history scope | mitigate | Query resident payment/receipt history through the existing RLS-protected browser client so former residents keep only their allowed read-only records. |
</threat_model>
