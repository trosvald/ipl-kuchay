# Phase 02 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

> **Redesign note:** This contract replaces the previous Phase 02 UI-SPEC with a research-informed redesign. The current UI relies on flat tables, uniform cards, and neutral-only color with no visual hierarchy — identified as misaligned with modern community/residential management app UX. This contract introduces financial-status color semantics, card-based invoice layouts, per-kavling tab grouping, skeleton loading, confirmation dialogs, and a neighborhood-appropriate visual warmth that matches Indonesian residential context apps.

## Visual Design Principles

These principles guide the redesign away from the current flat-table UI toward a modern community billing experience.

### 1. Financial Information Hierarchy
- Arrears and totals are the first thing residents see, presented as large-format metric cards with semantic color.
- Invoice details are secondary, shown on expandable cards below the summary.
- The visual weight hierarchy: Arrears Total > Per-Period Summary > Fee Item Detail.

### 2. Card-First, Table-Second
- Resident billing view uses card-based invoice layout exclusively — not a flat table.
- Admin billing period list may use tables for dense data, but key actions use Dialog/Sheet overlays.
- Card borders use subtle 1px `border` with `rounded-xl` (12px radius) for warmth appropriate to a residential app.

### 3. Neighborhood Visual Warmth
- White backgrounds with `rounded-xl` cards feel residential, not enterprise.
- Status badges use full background-tint treatment (not outline-only) so color tells the story at a glance.
- Summary metric cards use large Display-size numbers with appropriate semantic color.
- Empty and loading states use card containers with centered illustration text, not bare text.

### 4. Progressive Disclosure
- Invoice cards show summary row by default (period, status badge, total, due date).
- Fee item breakdown is hidden until the resident clicks/taps the expand trigger.
- Admin generation preview opens in a Dialog overlay, not an inline expansion.
- Penalty application preview opens in a Sheet (desktop) or Dialog (mobile).

### 5. Mobile-First Touch Targets
- Kavling tabs meet 44px minimum touch height.
- Invoice card expand triggers have 44px minimum tap area.
- Action buttons in cards use `h-10` minimum height (`40px`) approaching the 44px mobile target.
- Filter controls use full-width select on mobile, inline on desktop.

## Interaction Contract

### Resident Billing View — Arrears Summary

- The top of the resident billing page starts with an arrears summary card before any invoice list.
- If the resident has overdue/unpaid invoices, the arrears card shows the total overdue amount in red (`destructive` foreground) at Display size. Background uses a subtle destructive tint.
- If the resident has no arrears (all invoices paid or current), the arrears card shows a green success state with text "Semua tagihan Anda sudah lunas."
- The arrears card includes a secondary line: jumlah invoice yang belum dibayar (e.g., "3 tagihan belum dibayar").

### Resident Billing View — Per-Kavling Grouping

- For multi-kavling residents, billing is organized using Tabs (shadcn Tabs component) with one tab per kavling.
- Tab labels: "Kavling {code}" (e.g., "Kavling A5", "Kavling B12").
- On mobile, kavling tabs remain as a horizontal scrollable TabsList (not dropdown).
- Single-kavling residents see their kavling code as a section heading instead of tabs (no tab chrome for a single item).
- Totals remain per-kavling; never merge household totals into one combined ledger.

### Resident Billing View — Invoice Cards

- Invoice list is card-based, ordered by newest due date first within each kavling.
- Each invoice card summary row contains:
  - Period label (e.g., "April 2026") at weight 600, size 16px
  - Status badge with full semantic background tint (green/amber/red/gray)
  - Total due amount at weight 600
  - Due date in `formatDateId()` format
  - Expand affordance (chevron-down icon from lucide-react)
- Clicking the card or chevron expands the breakdown inline within the same card.
- Expanded content shows fee items in this order:
  1. `Iuran Rutin` section — recurring/default fee items
  2. `Biaya Khusus` section — override-applied fee items (if any), with a small "Override" label
  3. `Denda Keterlambatan` section — penalty items (if any)
- Each fee item shows: name, resolved amount, and source label ("default" or "override").
- Expand/collapse uses Accordion-style animation (200ms ease-in-out).

### Resident Billing View — History Visibility

- Archived and closed periods remain visible in the same billing surface as history.
- They are styled with reduced visual emphasis: heading uses `text-muted-foreground`, no primary accent, badge shows gray/muted status.
- History cards are not removed or hidden — they are visually de-emphasized, not disabled.

### Admin Billing Configuration — Period Lifecycle

- Billing period list uses a table layout (admin-appropriate for dense data).
- Each row shows: period label, due date, status badge (with semantic background tint), invoice count, and action buttons.
- Status lifecycle is presented as a visible label on each row, not a separate stepper. Draft rows have a muted badge; open rows have an info-blue badge; closed rows have a neutral badge; archived rows have a secondary-muted badge.
- Lifecycle action buttons (`Open`, `Close`, `Archive`) are explicit text buttons with appropriate variants:
  - `Open` → `variant="default"` (accent)
  - `Close` → `variant="secondary"`
  - `Archive` → `variant="destructive"` (only appears when status is `closed`)
- Draft status visually differentiates from open: draft period row uses `bg-muted/50` row background and a subtle "Konsep" badge.

### Admin Billing Configuration — Invoice Generation Preview

- `Generate Tagihan` / `Terbitkan Tagihan` opens a Dialog overlay (not inline).
- Dialog title: "Pratinjau Tagihan — {period label}"
- Dialog content: a table showing kavling, fee items, resolved amounts, override/default source, and period total.
- Dialog footer: Cancel (secondary) and `Konfirmasi dan Terbitkan` (default/primary) buttons.
- After confirmation, show an inline success notice below the period row and refresh data.

### Admin Billing Configuration — Penalty Application

- `Terapkan Denda` opens a Sheet (slide-in from right on desktop) or Dialog (mobile).
- Content: preview table showing overdue invoices eligible for penalty, with cycle key clearly labeled (e.g., "Siklus: 2026-04").
- Sheet/Dialog footer: Cancel and `Konfirmasi dan Terapkan Denda` (destructive variant for the action, since it's irrevocable).

### States

- **Loading:** Show card/table skeleton blocks (shadcn Skeleton) for primary list areas. Never show "Memuat..." text alone. Resident billing skeleton: 3 skeleton cards with pulse animation. Admin table skeleton: header row + 5 skeleton rows.
- **Empty:** Show a centered card with calm illustration-style text, a heading, and a brief explanation. Never show an error color for empty state.
- **Error:** Inline alert card above the affected surface with destructive tint, clear problem description, and a recovery action button ("Muat Ulang").
- **Success after admin confirm:** Brief inline success banner near the acted-on period with checkmark icon, then refresh data after 2 seconds.

## Design Decisions Rationale

### Why Card-Based Invoices Instead of Table

The current `ResidentInvoicesPage.tsx` renders a flat table with columns for invoice number, period, kavling, due date, status, amounts, and action link. This is a data-dense but cognitively poor layout for residents who need to quickly answer "what do I owe?" and "am I overdue?". Modern residential billing apps (TownSq, Buildium, Rukita) use card-based invoice layouts with:
1. A prominent total at the top
2. Per-item cards with expandable details
3. Color-coded status that's scannable without reading text

This redesign adopts this pattern because the primary resident task is understanding their financial obligation, not scanning a 900px-wide table.

### Why Financial Status Colors

The current UI uses only neutral/badge variants with no semantic color connection to financial states. In residential billing, residents need immediate visual feedback:
- Green = good (paid, closed, on-track)
- Amber = caution (pending, partial, almost due)
- Red = urgent (overdue, rejected, requires action)

This is standard in every modern billing/finance app and is especially important for a neighborhood app where residents may not check frequently.

### Why Arrears Summary First

CONTEXT.md decision D-06 specifies "arrears summary card at the top." This contract makes it visually prominent with a large monetary display and semantic color, because the number one question from residents is "how much do I owe in total?" The arrears card answers this before any scrolling.

### Why Dialog/Sheet for Preview-Confirm

CONTEXT.md decisions D-01 and D-08 require preview-then-confirm flows for invoice generation and penalty application. Using Dialog (and Sheet on desktop for penalty preview) follows the shadcn pattern for destructive/irreversible confirmations and ensures the admin sees the full preview in a focused overlay rather than an inline expansion that could be accidentally skipped.

### Why Shadcn Tabs for Per-Kavling Grouping

CONTEXT.md decision D-04 specifies per-kavling cards or tabs. Tabs provide the cleanest UX for multi-kavling residents because:
1. Each kavling's invoices are isolated and scannable
2. Tab labels are always visible for quick switching
3. On mobile, tabs scroll horizontally (standard pattern in community apps)
4. Single-kavling residents see a section heading instead (no empty tab chrome)
