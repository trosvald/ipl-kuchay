# Phase 04 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

> **Direction note:** This phase extends the existing neutral shadcn system into a resident command-center experience. `/app` must feel terpercaya, ringkas, dan resmi — billing stays first, announcements read like a neighborhood notice board, and events stay actionable without becoming a social feed.

Never use accent for every badge, every link, or all announcement/event cards.

These extend the existing neutral system without replacing it.

| State | Background | Foreground | Usage |

- Urgent amber is reserved for urgency semantics only; do not use it for general warnings unrelated to announcements.

- Billing cards on `/app` continue using the Phase 02 financial semantics; Phase 04 must not replace those colors with announcement/event colors.

## Visual Design Principles

### 1. Billing First, Always
- `/app` is a resident dashboard, not a mixed-content news feed.
- Billing summary sits first and remains the highest-contrast section on the page.
- For multi-kavling residents, each kavling gets its own summary card; never show one merged household total.

### 2. Official Notice Board, Not Social Feed
- Announcement cards prioritize publish date, urgency, title, and short summary.
- Do not surface author avatars, reaction counts, or comment affordances.
- One urgent hero may lead the page; everything else becomes a compact notice card.

### 3. Actionable Events Without Detail-Page Dependency
- Event cards must show date, time, location, short description, current RSVP state, and a clear next action.
- Residents should understand an event from the list view before opening detail.
- RSVP editing belongs to the resident and remains editable until event start.

### 4. Compact Preview, Deep Detail
- Home sections show slices only: billing summary, one urgent hero, one-to-two latest announcements, and a short upcoming-events slice.
- Dedicated resident pages carry the full feed and detail depth.

### 5. Role-Sealed Admin Chrome
- Admin announcements and admin events are separate pages.
- Treasurer must not see create, publish, unpublish, archive, cancel, or RSVP-management affordances.
- Resident shell may still expose `/admin` to treasurer, but communication/event routes must not appear in treasurer navigation.

## Interaction Contract

### Resident Home (`/app`)

- Page order is locked:
  1. `Ringkasan Tagihan`
  2. urgent announcement hero (or latest published announcement fallback)
  3. `Pengumuman Terbaru`
  4. `Acara Mendatang`
- Billing section uses separate cards per kavling, ordered primary kavling first, then alphanumeric kavling code.
- Each billing card shows: kavling code, outstanding/arrears summary, unpaid invoice count, nearest due date, and `Lihat Tagihan` CTA.
- No combined household total may appear above or beside the per-kavling cards.
- Home announcement slice shows at most one hero plus two compact preview cards.
- Home events slice shows at most three upcoming events.
- If announcement or event data fails while billing succeeds, billing still renders and the failed slice shows its own inline error card. Do not blank the full dashboard.

### Resident Home — Urgent Announcement Hero

- Show only one pinned urgent hero at the top of the non-billing content.
- Hero content: urgent badge, publish date, title, 2-3 line preview, up to 3 attachment chips, `Baca Pengumuman` button.
- If no urgent published item exists, reuse the hero layout for the newest published announcement but without urgent tint.
- Additional urgent items do not stack as heroes; they return to the normal list with `Penting` badge.

### Resident Announcements Feed (`/app/announcements`)

- Layout is card-based, newest published first.
- Top of page may repeat the single urgent hero if one is active.
- Non-hero cards show: publish date, urgency badge if relevant, title, 2-line preview, attachment chips, `Baca Pengumuman` CTA.
- Published active feed and archived history are visually separated:
  - active section heading: `Pengumuman`
  - archive section heading: `Riwayat Pengumuman`
- Unpublished items never appear in resident UI.
- Archived items appear only in the history section, using muted surfaces and reduced emphasis.

### Resident Announcement Detail (`/app/announcements/[id]`)

- Header contains back link, title, urgency badge if relevant, publish date, and archive badge if the item is historical.
- Attachments appear directly below the metadata as chips or thumbnails with explicit open/download affordance.
- Body text uses 16px body size with max comfortable reading width inside a card container.
- If the item was archived, show a muted note above the body: `Pengumuman ini berada di arsip dan disimpan sebagai riwayat informasi warga.`

### Resident Events Feed (`/app/events`)

- Use Tabs for the three resident states in this exact order: `Mendatang`, `Dibatalkan`, `Selesai`.
- Each tab label may include count badges.
- Event cards must show in-list: date, time, location, short description, current RSVP state, and main CTA.
- Upcoming cards use normal emphasis; cancelled cards use destructive badge plus neutral card body; past cards use muted surfaces.
- Resident cannot edit RSVP directly from a cancelled or past card.

### Resident Event Detail + RSVP (`/app/events/[id]`)

- Detail header shows title, date, time range, location, and status badge.
- Description appears above RSVP controls so the resident can understand context before responding.
- RSVP control is a 3-choice segmented group in this exact order:
  1. `Saya Hadir`
  2. `Tidak Bisa Hadir`
  3. `Belum Menjawab`
- Current selection is visually highlighted; the other two remain outline/secondary.
- RSVP remains editable until the event `starts_at` time.
- When the event has started, finished, or been cancelled, the control becomes read-only with inline explanation:
  - started/past: `RSVP sudah ditutup karena acara telah dimulai.`
  - cancelled: `Acara ini dibatalkan. RSVP tidak dapat diubah.`
- After a successful RSVP change, show inline confirmation near the control, not a global toast only.

### Admin Announcements Management (`/admin/announcements`)

- This page is admin and super-admin only.
- Page structure:
  1. page heading + short helper text
  2. action row with `Pengumuman Baru`
  3. status filter tabs: `Draft`, `Terbit`, `Arsip`
  4. management table/list
- Each row/card shows: title, publish date or draft timestamp, status badge, urgent badge if set, pinned flag if set, attachment count, and actions.
- Save from the editor defaults to draft. Publishing is a separate explicit action.
- `Urgent` and `Pinned` are separate toggles in the editor. Helper copy must explain: `Beranda warga hanya menampilkan satu hero penting. Pengumuman penting lain tetap muncul di daftar.`
- `Tarik Publikasi` returns an item to a non-resident-visible state immediately.
- `Arsipkan` moves the item into resident history and admin archive tab.
- Archive and unpublish actions require `AlertDialog` confirmation; publish may use a lighter confirm pattern or explicit button press.

### Admin Announcement Editor

- Use a Dialog for create/edit, not inline expansion.
- Fields: title, body, status context, urgent toggle, pinned toggle, attachment area.
- Body input uses a multiline text area with plain-text or simple rich-text-safe formatting only; no social/editor chrome.
- Attachment area shows already-uploaded files as chips/rows with filename, type, and remove action.
- Primary footer actions:
  - draft item: `Simpan Draft`, `Publikasikan`
  - published item: `Simpan Perubahan`, `Tarik Publikasi`
  - destructive secondary action outside primary button group: `Arsipkan`

### Admin Events Management (`/admin/events`)

- This page is admin and super-admin only.
- Separate from announcements; never combine into one shared “content” workspace.
- Page structure:
  1. heading + helper text
  2. `Acara Baru` CTA
  3. tabs: `Mendatang`, `Dibatalkan`, `Selesai`
  4. management table/list with RSVP summaries
- Each row/card shows: title, start date/time, location, status, RSVP totals (`Hadir`, `Tidak Hadir`, `Belum Menjawab`), and action buttons.
- Cancel flow is explicit and non-destructive: the record remains visible to residents in the cancelled tab.
- `Batalkan Acara` requires confirmation and a cancellation note that will be shown to residents.

### Admin Event Editor + RSVP Summary

- Create/edit uses a Dialog.
- Fields: title, description, location, start date/time, end date/time, status note if cancelled.
- RSVP summary appears as a secondary card/table in the event detail or edit surface, not in the create form.
- RSVP summary order: `Hadir`, `Tidak Hadir`, `Belum Menjawab`.
- Treasurer must never see RSVP summary controls or event editing routes.

### Navigation Additions

- Resident shell adds two new navigation entries after `Tagihan` and before `Pengaturan`:
  - `Pengumuman`
  - `Acara`
- `/app` remains labeled `Ringkasan` and is the default resident landing page.
- Admin navigation adds:
  - `/admin/announcements` with label `Pengumuman`
  - `/admin/events` with label `Acara`
- These two admin items appear for `admin` and `super_admin` only.
- Treasurer navigation remains unchanged from the finance-only set.

### Shared States

- **Loading:** use skeleton cards/rows, never plain `Memuat...` text for primary surfaces.
- **Empty:** use calm neutral cards with one heading, one sentence, and one next-step link if relevant.
- **Error:** show inline alert card above the affected section with destructive tint and a `Muat Ulang` action.
- **Success:** show brief inline confirmation near the acted-on card or form footer.

## Design Decisions Rationale

### Why Separate Per-Kavling Billing Cards On Home

Phase 04 inherits the Phase 02 rule that resident billing stays separated per kavling. Summary cards preserve that contract while keeping `/app` compact. Tabs are appropriate on the full billing page; cards are better on home because the resident needs immediate scanability without extra interaction.

### Why One Urgent Hero Only

The context explicitly forbids stacking multiple pinned banners. One hero keeps urgency meaningful. Additional urgent items still remain visible in the feed, but they stop competing with the primary billing block.

### Why Events Use Three Explicit Resident States

`Mendatang`, `Dibatalkan`, and `Selesai` make the lifecycle legible and preserve trust. Silent removal of cancelled items would make residents unsure whether information changed or vanished by mistake.

### Why Treasurer Must Not See Content Management

The product already separates finance authority from broader admin authority. Communication/event tooling changes resident-visible information, so the UI must preserve the same role boundary even if generic admin shell helpers are broader.
